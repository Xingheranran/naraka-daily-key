# 永劫无间 · 每日金钥匙答案

自动收录官方公众号推文里的「今日金钥匙」，端游 / 手游双端都有，按推文日期归档成纯 JSON，附一个能直接看的静态网页。

- 网页：<https://xingheranran.github.io/naraka-daily-key/>
- 当前答案：`data/index.json` 里的 `current`
- 单日明细：`data/YYYY-MM-DD.json`

## 有效期规则

官方口径是「每日金钥匙在**次日下午 6 点前**有效」。所以：

- 推文在 **D 日**发布，里面的答案在 **D 日当天 ~ D+1 日 18:00** 都能用；
- 本站按推文日期归档，`D.json` 装的就是 D 日那篇推文的答案；
- 接口里的推文链接会**晚一天**更新，所以每天看到的是前一天发布的那条——这是正常的，不是漏抓；
- 过了 `D+1 18:00` 就不再出现在「当前有效答案」里，只留历史。

答案来自官方公众号推文的公开内容。本项目只做信息聚合，**不提供代刷、自动领取、账号操作等任何功能**。

## 数据格式

`data/2026-10-22.json`：

```json
{
  "date": "2026-10-22",
  "updated_at": "2026-10-23T20:39:51+08:00",
  "pc": {
    "answer": "今日更新",
    "confidence": 0.783,
    "source": "https://mp.weixin.qq.com/s/Y569r0b6t1V8xwP7PBzB7g",
    "title": "今日待办：出席鸿门宴，宛渠游泳健身，晚上听胡桃讲鬼故事",
    "published_at": "2026-10-22T11:55:45+08:00",
    "valid_until": "2026-10-23T18:00:00+08:00",
    "captured_at": "2026-10-23T20:39:47+08:00",
    "verified": null,
    "verified_at": "",
    "verify_note": "已过有效期，未验证",
    "ocr": ["今日金钥匙", "今日更新", "每日金钥匙在次日下午6点前有效", "使用方式："]
  },
  "mobile": {
    "answer": "速通指南",
    "confidence": 0.7624,
    "source": "https://mp.weixin.qq.com/s/0l9AuwkHfZy8xwFNFR_LtA",
    "title": "今日待办：跟随胡桃探索聚窟洲，在森罗谷与雪魔王拼刀",
    "published_at": "2026-10-22T12:48:20+08:00",
    "valid_until": "2026-10-23T18:00:00+08:00",
    "captured_at": "2026-10-23T20:39:50+08:00",
    "verified": null,
    "verified_at": "",
    "verify_note": "已过有效期，未验证",
    "ocr": ["今日金钥匙", "速通指南", "使用方式："]
  }
}
```

| 字段 | 含义 |
| --- | --- |
| `pc`、`mobile` | 端游、手游两端的答案，结构相同 |
| `answer` | 答案本身；缺这个字段说明这天没抓到 |
| `confidence` | OCR 置信度，低于 0.6 时值得人工核对 |
| `source` | 答案出自哪篇推文 |
| `title` | 推文标题 |
| `published_at` | 推文发布时间，北京时间 |
| `valid_until` | 这条答案的有效期截止，固定为发布日次日 18:00 |
| `captured_at` | 抓到的时刻 |
| `verified` | 验证结论：`true` 表示已确认能领到，`false` 表示试领失败，`null` 表示还没验证 |
| `verified_at` | 得出验证结论的时刻 |
| `verify_note` | 验证依据，例如「今日任务已完成」「领取成功」「领取失败：答案错误」 |
| `ocr` | 原图识别出的文本块，留作复核 |

`data/index.json` 是轻量索引：`current` 指向当前仍在有效期内的那条，客户端只看这一个文件就够；`days` 是全量历史。

```json
{
  "updated_at": "2026-10-24T09:12:31+08:00",
  "current": {
    "date": "2026-10-23",
    "valid_until": "2026-10-24T18:00:00+08:00",
    "updated_at": "2026-10-24T09:12:31+08:00",
    "pc": { "answer": "示例答案A", "verified": true, "verify_note": "今日任务已完成", "verified_at": "2026-10-24T09:12:30+08:00" },
    "mobile": { "answer": "示例答案B", "verified": null, "verify_note": "待验证", "verified_at": "" }
  },
  "days": [
    {
      "date": "2026-10-23",
      "pc": "示例答案A",
      "mobile": "示例答案B",
      "valid_until": "2026-10-24T18:00:00+08:00",
      "verified": null,
      "updated_at": "2026-10-24T09:12:31+08:00"
    }
  ]
}
```

> 上例中 `days[].verified` 是两端汇总：都通过才算 `true`，任一端失败就是 `false`，其余为 `null`。

## 这是怎么来的

官方每天会在公众号推文末尾放一张「今日金钥匙」图，答案就印在图上，文字很小、排版每天还不一样。整个流程三步：

1. **定时触发**——GitHub Actions 每 2 小时跑一次。拿到新推文就归档，同一篇不会被重复识别。
2. **取文末图片**——定位接口当前指向的那篇推文，取文末图片。推文都带发布时间，答案按发布日归档，有效期自动算到次日 18:00。
3. **OCR 提取**——离线 OCR 识别图里的文字，定位「今日金钥匙」后面那一段作为答案，识别结果连同置信度、原始文本块一起存进 JSON。

为什么不用人肉抄：每天两遍、字小、还容易看错，OCR 几秒钟出结果，原始文本块一并留档，真错了能查到是哪一步出的问题。

抓取端的实现放在私有仓库，这里只发布结果：答案、历史、以及读数据需要的东西。

## 关于 `verified`

答案发出来之后，程序会在下午尝试用它去兑换一次：

- 如果当天的兑换任务已经完成，说明答案确实能用，标 `true`；
- 如果还能兑换，就试一次，成功标 `true`，失败标 `false` 并记下原因；
- 验证不影响答案的发布——它只决定旁边那个标记是什么。

因为兑换每天只能成功一次，所以标记会晚一点出现；已经领过的日子也会直接显示为已验证。

## 怎么用

- 直接看网页，当前有效答案在最上面，标注了来源推文日期和有效期。
- 接自己的程序：读 `data/index.json` 的 `current` 即可；要给用户看历史再取 `days`。
- 细看某天：`data/YYYY-MM-DD.json`，文件名就是推文发布日。
- 找不到某天，说明那天没抓到（官方没发或识别失败），不是数据被删了。

## 勘误

OCR 偶尔认错字，尤其是生僻词。答案不对时到 [Issues](https://github.com/Xingheranran/naraka-daily-key/issues) 说一声，附上日期和正确写法，会回填修正。
